# The hub budget (ADR-012, rules `hub_enums_only_shrink` and
# `threads_apply_matches_no_screen_or_feature_intent`, tests/rules/layers.rs).
#
# The hub's enums have one variant per case of every feature that went through them. A new
# feature is a slice (core/src/features/<f>/, the recipe at the end of ADR-012 in docs/rtwk-port/architecture.md) and adds
# no variant here: each hub component carries one generic `Feature` variant. The numbers are
# what the code has, measured the day the framework landed (the generic variants of the
# framework included); a rule fails when a count rises, and when it falls, so that a feature
# that moves into a slice writes the saving down here and it cannot come back.
#
# enum <file> <Name> <variants>
# arms <file> <fn> <pattern> <occurrences of the pattern in the function's code>
# methods <file> <Trait> <methods of the trait>

# The slash list has no generic `Feature` variant yet: a Need of the ADR-012 owner.

# The framework's own hub: what a feature can say (`Out`) and the generated root's variants that
# are no feature's. A new one is a decision with an ADR-012 paragraph (a hook is added only for
# a thread or app lifecycle fact, never for one producer and one consumer), and raises its line.
# ADR-013 (the /plugins pilot): `Out` 8 -> 9 for the one-shot a feature leaves (`Wish`: the
# `SurfaceWish` queue) and `app.rs Intent` 15 -> 17 for what a
# surface says back, generic for every feature (`Interest`: the counter of the surfaces that show
# a feature's data; `WishShown`: the presenter showed a wish). `Feature` 16 -> 17 for
# `on_interest` (the first or last surface of an interest came or went), the one hook of the
# interest counter; `Wish` and `Interest` are types, not methods. The ids-only `Menu`, `Pick`
# and `Prompt` hooks of the trait stay until the families that use them have moved (ratchets).
enum core/src/features/cx.rs Out 9
enum core/src/features/mod.rs FeatureThreadIntent 1
methods core/src/features/mod.rs Feature 17
# threads::apply_ev still matches the chat screen's thread intents by name (the draft, the mask,
# ...): the count goes to 0 as they move behind `chat::apply_thread_intent` or into feature
# slices. The queue's five went to `threads/queue.rs` (`apply`, which gives back what is not the
# queue's): the queue is the thread's own lifecycle state, not a slice (ADR-012). A feature's
# thread intent is never named there.
arms core/src/threads.rs apply_ev ScreenThreadIntent:: 9
arms core/src/threads.rs apply_ev FeatureThreadIntent:: 0
