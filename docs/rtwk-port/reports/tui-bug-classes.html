Codex TUI bug history and the state-design rules that remove bug classes

508 bug-fix commits, 2025-04-25 to 2026-11-16. Which bugs came from where state lives, and which design rules would make each class impossible, caught by a test, or leave it open.

  1. 508 bug-fix commits touched codex-rs/tui and tui2 between 2025-04-25 and 2026-11-16 (of 3,612 non-merge commits since 2025-04-24). The busiest month is 2026-04 with 58.
  2. I read 135 of them, 24 more outside the subject filter, and 42 public issues. 55 fix-set commits, 23 outside commits and 34 issues are state-mechanism bugs. The rest are layout, terminal, text, backend and non-runtime changes.
  3. Three mechanisms cause 15 of the 55 commits and 15 of the 34 issues: a widget rebuilt and replayed on thread switch (SC2a), model state copied into child widgets (SC6a), and display flags set by hand (SC7a).
  4. With 14 design rules (R1 to R14), 28 of 55 commits become impossible by type or lint, 25 are caught by a test the rules require, and 2 stay possible. For issues the split is 13 / 16 / 5.
  5. As a share of all 508 fix commits that is 5.5% removed and 4.9% caught. A retained-mode widget framework alone removes about 10% of the 508 as a class (terminal and layout mechanics), shrinks about 27%, and leaves about 62%, with an error of about +-5 points.

2. State-mechanism bugs

The 55 fix-set commits, 23 outside-filter commits and 34 issues below share a pattern: two parts of the program disagree about the state of the world. Each sub-class has one root-cause mechanism. A commit counts once, under its primary sub-class. Feature-logic errors in a state transition (SC14, 16 commits) are not a state mechanism and are left out of the cards.

SC1 Stale async reply applied

6 fix-set commits, 1 outside the filter, 0 issues

A reply is matched by a per-widget counter or not at all. When the chat widget is replaced (resume, thread switch) the counter restarts, and an aborted task's reply can already be queued, so a stale reply is applied to a newer request.

  • 641e2e362 Ignore stale workspace headline requests and archived messages (#61411)
    Headline request counter restarted when the chat widget was replaced, so a previous widget's response matched a new pending request
  • 5ca2007ab Expose thread costs in statusline state and reject stale usage reads (#61410)
    Replacement chat widget accepted a previous widget's usage result for the same thread (no unique request id)
  • f046cf35d Scope model catalog caches to the current provider and auth identity (#43906) outside filter
    In-flight catalog refresh overwrote a newer account's catalog; cache reused across provider/auth identity
  • c8949e55c Ignore stale refresh responses in agents overview tests (#51064)
    Aborting a refresh task cannot retract a response already queued; helper consumed the stale response (request id not checked)
  • 1f17a0a04 Prevent stale voice answers from reappearing during speech recovery (#47975)
    Recovered/replayed voice answers were not filtered by input generation and reappeared under a newer question

One ChatWidget holds a thread's state. A switch rebuilds it and replays a bounded buffer, then the queued live events. Replay can handle an event twice, miss one the buffer evicted, or let the previous thread's queued events leak in.

3. How the main mechanisms arise, and the target shape

Left: the shape of today's code. Events from several sources go through one bus into a controller that also owns widgets. Three mechanisms (red) produce most state bugs. Right: the target shape. Every change is a value in one ordered stream, applied per thread with ids checked, into one model; views are derived from it. Rule numbers (R1 to R14) refer to section 4.

A single dispatcher is not what removes the classes: the code already sends 335 AppEvent variants through App::handle_event and has every sub-class. Where state lives, and the types used for ids, threads, lifecycles and transcripts, decide.

4. The rules

Each rule is named after what makes it hold: a type, a lint, or a test the design makes mandatory. Impossible means the compiler or a CI lint rejects the program; caught means a required test fails.

7. Method and limits

  • Selection. git log --no-merges -- codex-rs/tui codex-rs/tui2 gives 3,612 commits. A subject regex (fix, bug, regress, revert, panic, crash, hang, flicker, glitch, garbl, corrupt, broken, stale, duplicate, race, leak, deadlock, freez) selects 508. Each commit gets a primary class from an ordered subject regex. The 169 'other' commits are mostly backend, config and CI text; a 50% sample read found about 80% non-UI.
  • Reading. 135 fix-set commits were read for root cause: all 111 state_ui and race commits, and 24 state-flavoured commits from other classes (subjects with stale, switch, resume, duplicate and similar). For each I read the commit message (Codex PRs carry Why and What sections) and, where it was empty or vague, the TUI diff. 24 commits outside the fix set were read the same way. Total 159 commits. One reader, one primary sub-class per commit; root causes come from commit text and diff reading, not from reproduction.
  • Unread part. 373 fix-set commits (mostly terminal, layout, key and backend classes) were not read for state mechanism. The state-mechanism count (55) is therefore a floor for the fix set. The class-level shares in section 1 are estimates with an error of about +-5 points; sub-class counts are counts of reviewed items and carry no sampling error for the 159 read, but they say little about unread commits.
  • What the subject filter misses. Subjects shaped like 'Preserve / Keep / Clear / Scope / Route ...' without a fix keyword give 106 more commits. A sample of 24 held 23 state-mechanism bugs, including the whole SC3 thread-routing series (8843960ba, 6f47fcb0b, 53a1f4c29). Taken at face value that is about 102 of the 106; a 95% Wilson interval for 23 of 24 is 80% to 99% (about 85 to 105 commits). The way the 24 were picked is not recorded as random, so treat this as a lower bound on how large the class is: the 508 undercount state bugs. The rules cover the 23 in similar proportions (10 impossible, 12 caught, 1 possible).
  • Issues. GitHub search on openai/codex, label TUI, keyword in title (stale, desync, out of sync, not updated, wrong thread, after resume, after switch, duplicate, race, doesn't update, not refresh, still shows, switching, disappear, reappear, stuck): 171 hits, 150 unique. 42 state-looking issues were read. The mechanism comes from the reporter's analysis or the linked fix; the cause of #30714 is not confirmed. 37 of the 42 are closed.
  • Verdict scale. Impossible: the type system or a CI lint rejects the program. Caught: a test the design makes mandatory fails. Still possible: anything else; 'careful code avoids it' counts as possible. * marks sub-classes where today's mechanism is absent from the design but the same bug can be written. Verdicts were reasoned on paper; nothing was implemented and run. 'Caught' assumes the required tests are written; 'impossible' assumes the lints are in CI.
  • Not in scope. The layout, terminal, text, style and input classes are covered in bug-classes.md, not here. Backend, persistence and feature-logic commits are counted but not analysed.
  • Code claims. Counts such as 335 AppEvent variants and the unwrap_or_default sites in chatwidget/tool_requests.rs were re-checked against the checkout of 2026-11-17.
