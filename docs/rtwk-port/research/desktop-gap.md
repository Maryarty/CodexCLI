# Codex Desktop app vs CLI TUI: phase-2 gap input (research dated 2026-11-17)

Method: official docs (developers.openai.com/codex/* now 308-redirects to learn.chatgpt.com/docs/*; pages carry no dates, changelog entries do), changelog, launch coverage, and the local inventory (codex-tui-features.csv, 312 rows; codex-tui-surface.md). App installed locally: no (/Applications has no Codex*.app).

IMPORTANT FRAMING. Two facts change the premise "Desktop has what CLI lacks":
- Since 2026-07-09 (secondary sources only) the standalone Codex app is the "Codex" mode of the unified ChatGPT desktop app (modes Chat / Work / Codex; macOS+Windows). "Codex Desktop" in docs now means that.
- The CLI TUI snapshot we port already contains much of what used to be Desktop-only: side conversation panes, sidebar, agents command center, worktrees popup, review flows, async questions, pets, voice, plugins, usage, cloud/remote backends (ids in table). The real gap is smaller and shifts to: visual review pane with staging/inline comments, integrated terminal tabs, browser/computer use, scheduled tasks inbox, file artifact viewer, projects model, mobile/remote relay.

## 1. Summary: top 10 Desktop capabilities for a terminal UI

| # | Capability | Verdict in a terminal |
|---|---|---|
| 1 | Many concurrent chats/agents across projects, each in its own worktree, with unread/running/needs-input status (Activity view, sidebar, pinned chats) | Feasible, native form. CLI already has agents command center (0.149+, 0.167) and sidebar; needs a multi-thread UI state model |
| 2 | Review pane: diff scopes (unstaged/staged/commit/branch/last turn), stage/unstage/revert per file or hunk, commit/push/PR | Feasible as a TUI diff view with hunk actions; mouse optional. CLI has /diff + /review, no staging |
| 3 | Inline diff comments (hover +, line-anchored) sent back to the agent; PR review plugin (GitHub GA, GitLab preview) | Feasible as cursor-anchored comments in a diff pane; PR checks/comments need an API-backed model |
| 4 | Git worktrees per chat, handoff Local<->worktree<->remote host, snapshots, .worktreeinclude, local-environment setup scripts and actions | Feasible (logic is in app-server/git); TUI needs thread<->checkout binding and picker. CLI has /worktree popup |
| 5 | Scheduled tasks / automations with Scheduled inbox, unread runs, background worktrees, heartbeat follow-ups in the same thread | Needs a different form: a daemon/scheduler outside the TUI process; TUI is only the inbox and editor. Docs say CLI has no Scheduled management UI |
| 6 | Integrated terminal tabs per chat, agent can read output; actions as top-bar buttons | Possible but awkward: nested PTY pane inside a TUI (embedded terminal emulator). Alternative: leave to tmux; keep /ps background terminals |
| 7 | In-app browser: preview, annotate elements, Adjust, agent browser use; Computer use (macOS/Windows) | Impossible natively. Terminal form: open external browser, show screenshots via kitty/sixel, text DOM/selector comments. Computer use is an app-server/agent capability the TUI only surfaces approvals for |
| 8 | Artifact/file viewer sidebar (PDF, slides, sheets, HTML, LaTeX preview, annotation) plus summary pane (plan, sources, files) | Partly: summary pane and text/markdown/image preview feasible; rich formats degrade to external open. CLI has sidebar+file cell, no Office/PDF |
| 9 | Remote: SSH remote projects, mobile relay (QR pair, approve from phone), host handoff, notifications (Activity view, floating pet, per-event alerts) | TUI can be the host or a remote client; mobile relay is server-side. TUI needs backend-agnostic threads and OSC notifications (exists) |
| 10 | Projects model (multi-folder projects, primary folder, pin, archive, project switcher, resume after crash) plus Settings UI and command palette (Cmd+K) | Feasible: switcher + palette are natural in a TUI; settings UI exists as /config panel. Needs a project registry independent of cwd |

Impossible or needing a different form: 7 (browser/computer use), 8 (rich formats), 6 (nested PTY, nonstandard), 5 (needs host process), 9 mobile relay (not a UI feature), pixel-level hover and drag affordances in 3.

## 3. Architectural requirements, ranked (what phase 1 must not preclude)

1. Threads are first-class entities independent of the visible widget. A store holds N threads (state, transcript, pending approvals, unread flag, backend, cwd/worktree) and routes events to the right one whether or not it is displayed. Needed by: concurrent agents, Activity view, notifications, side chats, scheduled-run inbox, cloud/remote lists. Upstream already moved this way (agents command center, side panes); the 130k-line `app/` + ~600 `AppEvent` shape suggests this is where rtwk's state-management ADR matters most.
2. Layout is a tree of panes, not a fixed "transcript + bottom pane" stack. Pane kinds to allow: chat, side chat, diff/review, file/artifact preview, summary, terminal, agents list, inbox. Needs focus management, resize/zoom, per-pane keymap context, per-pane own composer, and persistence of the layout. Current inline viewport (term.inline-viewport, history-insertion into scrollback) is a single-column design; phase 1 must keep an owned/fullscreen mode path (transcript_view already exists) where panes can live.
3. Modal vs persistent separation. Today `BottomPaneView` replaces the composer (modal). Desktop surfaces are persistent and non-modal (review pane stays while chatting; comments accumulate). Architecture should support both an overlay/modal stack and docked persistent views.
4. Execution environment is a mutable binding on a thread (host/backend, project, worktree, sandbox). Handoff, worktree creation, remote SSH, and cloud all rewrite it. Avoid hard-wiring cwd into global state.
5. Project/workspace registry above sessions: projects (multi-folder, pinned, archived), workspace switch (0.166 ChatGPT workspace switching), layout and open-thread restore on startup.
6. Structured diff and annotation model: hunk-addressable diff with scopes, stage/revert actions, and a comment store anchored to file/line that survives refresh and can be serialized into a prompt. Shared by `/diff`, `/review`, approval patch preview, and PR review.
7. Single action registry (commands, keymap, slash, command palette, buttons/actions from local environments) so features are invokable from any surface.
8. Notification and attention bus: events (turn done, approval, question, scheduled run finished) with focus-awareness, delivered via OSC 9/777, badges, pet, and status line.
9. Multi-client consistent pending-state: an approval or question can be answered from another client (phone) or another pane; UI must tolerate state resolved externally.
10. Pluggable renderers and previewers: image protocols (kitty/sixel/iTerm) already hard; artifact previews (PDF/office) via external helpers; the cell/renderable abstraction should allow async-loaded content and fallbacks.
11. Embedded PTY pane capability (vt parsing, key capture escape hatch, resize) - lowest priority, large cost; decide early whether it is in or out.
12. Daemon-friendly design: scheduler and long-running work outside the TUI process, TUI a client of app-server (already the case; `codex agents --no-daemon` exists in 0.167).
