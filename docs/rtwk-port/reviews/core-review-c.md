## (a) Verdict

1. Three defects. In each, a screen model takes a user action into an outbox that nothing reads.
   Ctrl+O in `/warnings` copies nothing (D1). A `/pets` pick is neither saved nor shown (D2).
   `approvals::Model` is a second copy of the request queue that nobody uses (R7).
2. Perf defect: every `AppEv::Clock` makes a deep copy of `ScreenStates`. That copy includes the
   agents thread list and the resume rows, because four screens each keep their own copy of the
   clock (D3). This costs us against the oracle on every timer tick of a running turn.
3. ADR-013 holes the rules miss. The rules match draw state by field name and gestures by exact
   variant name. So `/usage` tabs and metrics, the transcript pager's open state, resume's
   `Change(Control, Dir)`/`Paste` and agents' `TogglePin`/`CycleGrouping` all pass. Usage and the
   pager are in no departure list (R1–R3).
4. The main seam is `select`. Eight command families share one screen, three budgeted hub enums,
   690 lines of glue in `app/select.rs` and a private wish queue. Each new verb edits shared files
   (R10).
5. Screens have five ways to send work out and twelve request counters, none of them
   `Ticket`/`Pending`. One `AppFx::ask` door would remove them and the drop-the-RPC trap in the
   slot path (R11, R12).

## Answers by question

1. **Architecture holes.**
   - ADR-003: R5 (routing in a screen), R6 (open-in-flight copies), R7 (second request store),
     R8 (R5 transient state), R9 (no target thread), R14 (snapshots in intents).
   - ADR-013: R1, R2 (drawn state with no departure), R3 (what the name scans miss).
   - Rules that are missing: `screen_outboxes_have_a_reader` (D1, D2, R7), the gesture prefix and
     `Dir` payload checks (R3), the R13 widening (R4), clock fields in screens and all-`Shared`
     slots (D3), and the counter and `Loading` ratchets (R12, R13).
2. **Seams.**
   - `select` (R10) forces edits in select.rs, `app/select.rs`, `app.rs` and the budget file.
   - Screen hooks named in `app.rs` (N2).
   - `set_now` and `slot!` name screens (D3).
   - The output mechanisms (R11).
   - Doors: half-slices per select family, generated screen hooks, a `Now` provider with every
     slot `Shared`, and `AppFx::ask`.
3. **Structure.**
   - Onboarding is 1138 lines of production code plus 650 of tests and is split by concern. Its
     real problem is the bool-and-counter lifecycle (R12), not its size.
   - Core logic is duplicated in `src/pages` (R14) and words are built in core (N6).
   - Test machinery in live enums: chat's `Ev::Details/Pending/ProviderError { thread: String }`
     exist for fixtures only (chat.rs:296-307). Same class as A-F9.
4. **Duplication, dead code, perf.**
   - Duplication: loading enums (R13), counters (R12), wire builders (N5), two wish queues (R10).
   - Dead code: D1, D2, R7, and `agents::apply_intent`/`resume::apply_intent` (R11).
   - Hot-path perf: D3, N4.
   - Stringly typed: R4, N7.

## (c) Top 5 by payoff / cost

1. **D3: one clock, every slot `Shared`** (120 lines, low risk). It removes a deep copy of
   `ScreenStates` plus the agents and resume models on every clock event, removes two hub edits
   (`set_now`, `slot!`) and comes with its rule. Clashes with nothing.
2. **D1 + D2 + R7: the dead outboxes, plus `screen_outboxes_have_a_reader`** (about 150 lines,
   mostly deletions). Two user-visible defects close (warnings copy, pets pick), one parallel store
   goes, and the rule stops the next one. Feedback's `note` needs a word with w2-commands.
3. **R3 + R4: widen the ADR-013 and R13 scans, ratchet today's hits, then fix R1 and R2** (rules
   about 60 lines, ratchet lines; R1/R2 about 260). This is cheap and catches whole classes that
   pass today. Usage and the transcript pager either get a debt task on the ratchet or a fix.
4. **R11 + R12: `AppFx::ask` as the one door for screens** (about 300). It replaces twelve counters
   and four output mechanisms with the `Ticket`/`Pending` R1 already requires, removes the
   drop-the-RPC trap, and shrinks `app.rs`'s per-screen arms. It makes R10 cheaper. Do it before
   W3 adds screens.
5. **R10 (with R9): `select` families to half-slices, one at a time, after w2-commands lands.**
   Apps, models and permissions first (300-600 each). This is the biggest hub relief for W3: the
   select budget lines go down per family. Each family's `Ctx` carries its `ThreadId` as it moves,
   which closes R9.

Left to the person or orchestrator: whether R1 (usage) and R2 (pager) become debt tasks on the
ratchet or are fixed now; whether `voice`/`composer`, as empty slots, stay in `screen_list!`;
whether R5 and R8 go to core-review-a's follow-ups (they touch `app.rs`/`threads.rs`).
