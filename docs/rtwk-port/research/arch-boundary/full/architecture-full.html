0. Что строим и в каком порядке смотреть

1.3 IO-тест: где живёт значение

Вопросы задаются по порядку, и первое «да» решает:

  1. Это ответ или факт сервера или host, или выведено из них? → Д, core.
  2. Это параметр запроса или статус операции, без которого ответ не к чему приложить? → З, core. Это кэш по параметру, а не «текущее X»: core хранит Map<Key, Remote<T>>, а не «открытая деталь».
  3. От этого зависит шаг жизненного цикла (старт потока, очередь, запуск) или это сигнал, который домен посылает поверхности, — открыть её или положить текст в контроллер? → Ж, core.
  4. Домен должен знать, нужны ли данные прямо сейчас (загрузка при открытии, опрос, перезапрос после переподключения)? → И: счётчик в core, сам факт открытия в UI.
  5. Иначе → Н, UI.

Уточнения, которые снимают спорные случаи:

  • Текст поля ввода всегда Н (контроллер). Core получает его только глаголом при отправке или поиске (Submit, Search{query}) и никогда не пишет обратно. Если домену нужно изменить текст, он шлёт Directive (§4.6).
  • «Другой экран читает» — не довод. Довод — кто пишет. Значение, которое пишут только жесты одной поверхности, — это Н, даже если его читают двое: тогда его поднимают к общему предку в UI (ThreadUi, UiState), а не в core.
  • Ошибка, видимая до следующего действия пользователя: факт — Д с seq, «погашено» — Н (UI помнит последний погашенный seq).

1.4 Инварианты (каждый закреплён правилом, §13)

  1. Один писатель. Состояние приложения меняет только apply/apply_app на UI-потоке. Все входы идут через один ingress в порядке поступления (R10).
  2. Core без UI и IO. В core нет rtwk, tokio, часов, файлов и прозы. Это держит компилятор (манифест) и сканы.
  3. IO только в shell. Спавн, RPC, файлы, буфер обмена, часы — только в shell (R1, R11, R12).
  4. Аргументы — id, не данные (R14). Маршрут, шторка или диалог получает id и читает данные через провайдеры. Копию берёт только редактор, и это его черновик.
  5. Ни одного тикета в UI. UI сопоставляет ответы по доменному ключу операции (§4.5).
  6. Нарисованное не попадает в core. Скан по типам, достижимым из корней домена (§13).
  7. Слова только в UI (ADR-010). Core отдаёт ключи заметок и ошибок как типизированные значения.

4. Пути

4.1 Событие сервера (d5)

app-server → host (in_process.rs) → Ingress { backend, epoch, ev } → shell → UiApp::ingest → CodexApp::ingest. Там сверяется эпоха (R1): чужая — отбросить. Дальше apply_event → threads::project / project_unrouted → threads::apply(ThreadEv) и screens::project_thread → доменные части. Результат — AppFx.

После ingest UI делает:

  1. follow_core — создаёт ThreadUi новых потоков и удаляет их у закрытых *(новое)*;
  2. presenter-ы: запросы, желания;
  3. shell::run_effects(fx);
  4. view перезапускается, проекции получают новые Rc, перестраиваются только select-нувшие.

4.2 Жест → глагол (d6)

Жест обрабатывает сам виджет: Shortcuts/Actions или мышь. Если жест меняет только Н, это локальный setState или вызов контроллера, и до core он не доходит. Если меняет Д/З/Ж, виджет делает cx.emit(&hs.<handler>, verb). Обработчик кладёт AppEv::Intent(...) в ingress под текущей эпохой (R10): глагол не обгонит уже полученное событие. Глаголы называют намерение в терминах домена (Install{key}, Search{query}, NeedMore, OpenThread(id)), а не жест (Choose(row), Cursor(i), Toggle) — правило adr013_core_intents_name_no_gesture.

4.3 Эффект и ответ

apply кладёт эффект как данные:

  • AppFx/ThreadFx — RPC с тикетом из TicketMint;
  • effects::Ask — эффекты host.

Shell выполняет их через rtwk-tokio. Ответ приходит в ingress с тикетом и эпохой отправки → Pending::resolve (R1) → шаг владельца (answered, thread_answered, Reply::screen). Старый тикет отбрасывается.

4.4 Желание показать (d10)

Домен решает, что поверхность должна появиться (запрос сервера, установка требует авторизации приложений, стартовый промпт). Запросы сервера идут через RequestQueue, всё остальное — через SurfaceWish { seq, scope, kind }; фича пишет cx.wish(<f>::Wish). SurfacePresenter в UI — обобщение src/sheets/presenter.rs; решает он по модели в ingest, а не по проекции в том же flush (G14). Дальше:

  • если поверхность закрыта — открыть её с начальной страницей;
  • если открыта — она сама увидит желание через свой срез и перейдёт на страницу;
  • presenter шлёт WishShown(seq), core снимает желание.

Порядок как у оракула: запрос сервера встаёт поверх открытой шторки, после ответа шторка снова сверху (маршруты в стеке).

4.5 Операция фичи и её страница

  1. Шторка шлёт Install{key} и запоминает awaiting = (OpKey::Install(key), gen_before).
  2. Core: если ops[key] в полёте, игнорирует (двойное нажатие). Иначе ops[key] = Op { gen+1, Running } и ask.
  3. Ответ: ops[key] = Done(..) или Failed(..), заметка в транскрипт, при необходимости wish.
  4. Шторка выводит страницу как f(свой SheetStack, awaiting, ops[key]). Пока ops[key].gen <= gen_before, страница «загрузка» берётся из awaiting.
  5. Если шторку закрыли, ответ всё равно ложится в домен. Заметка появляется, а если оракул открывает поверхность и без пользователя — срабатывает wish.

4.6 Директива контроллеру (d11)

Домену иногда нужно изменить контроллер UI:

  • вернуть сообщения в композер (give_back, threads.rs:2995);
  • префилл после backtrack;
  • засеять историю из реплея;
  • очистить отправленное после подтверждения last_submit.

Это Directive<T> { seq, value } в ThreadModel. Слушатель по одному на род в widgets/directives.rs. Он сравнивает seq с ThreadUi.seen.<род> своего потока и применяет к контроллерам этого потока. Поток, который не показан, применяет директиву при показе: не теряется и не повторяется.

4.7 Интерес (d12)

Interest { key, child } берёт Hs в did_change_dependencies. В init_state он шлёт Interest(key, Open), в dispose_with — Close (rtwk разрешает emit там). Core:

  • счётчик 0 → 1: вызывает Feature::on_interest(open) (загрузить, начать опрос);
  • 1 → 0: on_interest(close) (остановить опрос, перестать ждать);
  • на attach: для каждого ключа со счётчиком > 0 снова on_interest(open).

4.8 Заметки и ошибки

Заметка в транскрипт — NoteKey (хаб) или FeatureNote с аргументами-данными, слова из strings.rs UI. Ошибка RPC — RpcError в Remote::Failed/Op::Failed, слова в UI. Ошибка поверхности до следующего действия — факт с seq, гасится в UI. Уведомления рабочего стола — DesktopNotice из AppFx (политика из [tui]), выполняет UI-обёртка TerminalEffects.

5. Жизненные циклы

5.1 Запуск (d8)

  1. host::main → arg0_dispatch_or_else → многопоточный tokio-рантайм → разбор CLI, язык (Cli::lang) → факты запуска (конфиг, auth, trust, обновление).
  2. run_app_view на потоке block_on с входом в рантайм (rtwk-tokio). UiApp::new(backend), UiState.awaits_facts = true.
  3. Shell стартует backend: in-process app-server, облачный или fake. CodexApp::attach() даёт эпоху. Подписка штампует ею события.
  4. Корневой view: MultiProvider (фиксированный список, G15) → Navigator (GlobalKey) → home StartupGate. Пока фактов нет, home пуст (оракул не мигает чатом до промптов).
  5. Факты (AppEv::Facts) → onboarding::Model: шаги sign-in, provider, trust, migration, import, стартовые промпты. Шаги — род Ж (они держат старт первого потока: FirstThread::AfterLaunch, start_held).
  6. StartupPage выводит текущий шаг как f(домен). Выбор внутри шага — Н, решение шага — глагол.
  7. Шаги кончились → apply_app стартует первый поток (ThreadAsk::Start). Композер работает как черновик и до Ready: отправка ждёт в queued_submits (R10).
  8. Ответ → ThreadSet::open(id, Origin) → session.active = id → follow_core создаёт ThreadUi → SessionPage в thread_scope(id).

codex-rtwk resume и codex-rtwk agents кладут start_resume / start_agents в UiState, и StartPage пушит соответствующую страницу над чатом.

5.2 Поток: открыть, переключить, закрыть (d9)

  • Открыть: любая страница (resume, agents, переключатель субагентов) шлёт Intent::OpenThread(id). apply_app решает так:
  • писатель уже держится → показать;
  • resume в полёте → ждать;
  • иначе выпустить один resume.

Esc отменяет навигацию, а поздний успешный ответ всё равно устанавливает единственного писателя. События до ответа attach копятся в attaching_events.

  • Переключить: session.active меняется только в apply_app. UI: thread_scope(new_id) перемонтирует поддерево потока, контроллеры берутся из ThreadUi[new_id] (черновик A→B→A цел, R2). Директивы B применяются по его seen. Шторки, привязанные к потоку (аргумент ThreadId), закрываются по предикату жизни. Докнутая шторка (О2) уходит вместе с поддеревом, как у оракула (replace_chat_widget). Шторки уровня приложения (/apps, /plugins, /status-диалоги) остаются.
  • Фон: каждый поток получает свои события и без показа (ThreadModel всегда актуален). Переключение не требует реплея в UI.
  • Закрыть (архив, удаление, отписка): ThreadSet убирает модель. follow_core удаляет ThreadUi[id] и через dispose освобождает контроллеры. Запросы сервера этого потока снимаются.

5.3 Переподключение (d9)

Disconnected → ConnectionState, баннер. Новый attach_backend(b) → новая эпоха, после чего:

  • (а) запросы сервера этого backend удаляются, и шторки запросов закрываются по предикату;
  • (б) все outgoing этого backend разрешаются Err(RpcError::Disconnected) *(новое, F6)*, Op/Remote → Failed;
  • (в) потоки переподписываются, снимок thread/read заменяет затронутые ходы (R4);
  • (г) интересы со счётчиком > 0 получают on_interest(open) снова.

Шторки остаются открытыми и видят Loading/Failed в своих срезах.

5.4 Выход

Hs.quit (Ctrl+C или Ctrl+D по правилам оракула, /quit, выход из шага onboarding) → AppCx::quit. fx.ends_app(): соединение не поднялось, host сообщает причину. Shell роняет клиента, задачи отменяются. Ctrl+Z приостанавливает приложение, внешний редактор тоже (ADR-006).

5.5 Шторка (d10)

  1. Открытие. Жест пользователя — страница зовёт features::open(cx, target) или sheets::<s>::open(cx, args). По воле домена — открывает SurfacePresenter. Аргументы: scope (поток или cwd), начальная страница, id.
  2. Монтирование. init_state создаёт контроллеры. Interest шлёт Open. Срез домена читается через select.
  3. Жизнь. Жесты меняют SheetStack и контроллеры, глаголы уходят в core, страница = f(стек, awaiting, срез).
  4. Закрытие — одной из четырёх причин:
  5. (а) пользователь (Esc на первой странице, выбор, который завершает);
  6. (б) предикат жизни стал ложным: запроса больше нет, scope устарел, поток сменился;
  7. (в) домен снял желание;
  8. (г) снятие поддерева.

В (а)–(в) шторка сама вызывает close_dialog или снимает свой слот. Решение принимается в did_change_dependencies по срезу, после flush, а не в том же flush, что и emit.

  1. dispose. Interest шлёт Close, контроллеры освобождаются, фокус возвращается открывшему (rtwk делает это для маршрутов; докнутая шторка возвращает фокус композеру явно).

6. Навигация и поверхности

6.1 Классы (поправка 2026-11-19b, без изменений по сути)

  • Страницы (PageRoute корневого Navigator): Startup (шаги), Session (home), Agents, Resume, Usage.
  • Режимы страницы — состояние её контроллера, а не новая страница: развёрнутый транскрипт (Ctrl+T, /diff, backtrack), активный поток (субагенты). Режим одного виджета ведёт его контроллер, второй копии виджета нет.
  • Шторки — виды нижней панели оракула: approvals, пикеры, настройки, pets, голос, /plugins, /apps, подтверждения.
  • Диалоги — центрированные виды оракула и настоящие диалоги (show_dialog).
  • Поповеры — /, @, $, поиск по истории (Autocomplete над композером).
  • Виджеты — ячейки транскрипта (/status — ячейка), строка статуса, футер, питомец.

6.2 Стек страниц шторки

SheetStack<P> *(новое, widgets/sheet_stack.rs)* — это State-владеемый Vec<Entry<P>>, где Entry { page: P, list: ListController, tabs: Option<TabController> }. Рисуется верхняя запись, нижние держат свои контроллеры: Esc возвращает родителя с курсором на исходной строке, и поле kept в core не нужно. Операции стека: push, pop, replace_top, reset(initial). Анимации и затемнения нет (паритет). Высота равна высоте верхней страницы. Вложенный Navigator для страниц шторки не используется: под ограниченными constraints его RenderTheater занимает всю высоту (rtwk navigator.rs:2650-2661). Другой путь — решение О1.

6.3 Где живёт шторка (О2)

Рекомендация: виды нижней панели оракула стоят в SheetHost *(новое)* — слоте в Column страницы сессии под транскриптом, внутри thread_scope. Это Scaffold.bottomSheet: хвост транскрипта поднимается над шторкой, как у оракула, а смена потока сбрасывает слот. SheetHost держит стек открытых шторок уровня потока (верхняя видна; запрос сервера всегда сверху). Центрированные виды и диалоги идут через show_dialog корневого навигатора. Шторки уровня приложения в debug-входах открываются на ближайшем навигаторе (seeded-scope, F9). До решения О2 шторки остаются, как сейчас, модальными маршрутами с sheet_options() (src/sheets/mod.rs:19-27), а правила §6.4 действуют одинаково.

6.4 Открытие и закрытие

  • Открывает только тот, кто просит: страница, фича (open) или presenter. Аргументы — id, scope, начальная страница (R14). Шторка не копирует доменные данные в State (r14_widget_state_fields_hold_no_model_types).
  • Каждая шторка объявляет предикат жизни fn alive(args, &срез) -> bool: запрос ещё в очереди, scope совпадает с доменом, поток активен. Ложный предикат → шторка закрывает себя. Правило: у каждой шторки есть alive (скан impl Sheet).
  • Шторка не решает по проекции в том же flush, в котором отправила глагол (G14): своё ожидание она хранит в awaiting.

6.5 Аргументы и результаты

Navigator::push::<T> / show_dialog::<T> возвращают результат. Если результат меняет домен, он уходит глаголом с доменным ключом, а не через сохранённый тикет. Страницы получают ThreadId/ключи. Редактор (настройки) копирует значение как черновик и возвращает его глаголом.

7. Фокус и клавиши

  • Владение. Разбор и разрешение tui.keymap.* (9 контекстов, аккорды, лидер) — в core (core/src/keymap), результат Rc<Keymap> в CodexApp (факт конфига). Каждая поверхность объявляет свои Intent rtwk (MoveDown, Accept, Back, NextTab…) и строит Shortcuts из контекста Keymap (src/keymap). Actions живут в State поверхности и вызывают контроллеры (Н) или шлют глаголы (Д).
  • Порядок. Фокус-дерево rtwk: маршрут → шторка/диалог → поле. Ближайший к фокусу Shortcuts берёт клавишу первым. back_key навигатора лежит слоем выше маршрутов (rtwk navigator.rs:1693-1699).   • Фокус при открытии и закрытии. Маршрут или диалог берёт фокус и возвращает его открывшему (rtwk). Докнутая шторка (О2) запрашивает фокус в init_state и отдаёт его композеру в deactivate.
  • Ввод никогда не замораживается RPC (ADR-006). Карантин набора перед approvals — gap G8. Задержка показа approval после набора (TYPING_IDLE_DELAY) — в presenter-е (UI).
  • Правило: KeyCode::/KeyPress::code только в src/keymap/ и примитивах widgets/ (ratchet от 280 вхождений в 31 файле). Подсказки футера строятся из тех же привязок, что и Shortcuts.

8. Мышь (ADR-011 без изменений)

Мышь — род Н: клик выделяет, клик по выделенному или двойной клик принимает, колесо прокручивает, вкладки и кнопки кликаются. Её обрабатывает виджет: Picker, session_list, tab_strip, SheetStack. 9. Ошибки и заметки

  • Ошибка — значение: RpcError (тикет, несовпадение, отказ, Disconnected), Failure потока, Problem экрана. Паник в путях apply нет.
  • Видимые слова ошибок и заметок — только в strings.rs UI. Core хранит ключ и данные (core_sources_hold_no_user_visible_prose).

Строки — типизированные const-таблицы, strings.rs на каталог UI (pages, sheets, features, widgets) и src/l10n/ для общих. Английский — текст оракула байт в байт. 11. Производительность

  • Горячие пути. Дельта стрима → threads::apply → select::<ThreadModel> активного потока → живой хвост транскрипта (один элемент, не чаще раза в кадр, ADR-004). Клавиша в шторке → локальный setState, перестраивается одно поддерево, core не участвует (C убирает курсоры из apply).
  • Срезы. ScreenStates и FeatureStates разбиты на Rc по экрану и по фиче *(новое)*, провайдер на срез, select по срезу. Клонируется только изменённый срез, и проснутся только его читатели. Запрещено watch целого ScreenStates/FeatureStates (ratchet от 27).
  • memo. Один уровень на регион. Ключи — дешёвые значения по строке или (rev, Rc<T>) (Versioned<T>). unchanged() в коде фич запрещён.
  • Виджеты. Экраны и шторки — stateful eq (ADR-002, условие 1). Списки — ListView с builder-ом (виртуализация). Монтируются только видимые экраны.
  • Измерение. ADR-008: pty A/B против оракула, 11 сценариев, отчёт с интервалами. Бюджет на сценарий масштаба (1 000 потоков, 30 панелей) — тест на релиз. Запас по семейству 4 (entities + notify) включается только по профилю выше ~1 мс на кадр.

0. Вердикт

Направление C верное. Принимать ADR-013 в черновой редакции нельзя: в нём четыре блокера. Диагноз отчёта подтверждается кодом: «модель экрана» в core, двери на каждую форму UI, дырявое правило. IO-тест разделяет состояние правильно. Но черновик держит только путь «жест → глагол → домен → проекция». Четыре других пути, которые оракул использует постоянно, в нём не описаны:

  1. домен сам открывает поверхность (оракул открывает шторку авторизации после ответа install, даже если пользователь её закрыл);
  2. домен пишет в контроллер UI (вернуть сообщения в композер, префилл после backtrack, запись истории);
  3. поверхность заявляет интерес к данным (открыта или закрыта), и домен должен знать это при переподключении;
  4. UI сопоставляет ответ со своим жестом, хотя тикет чеканит core.

Сверх того, предложенный механизм (вложенный Navigator в нижней шторке) в rtwk занимает всю высоту экрана. Всё это решается небольшими общими механизмами. Они описаны в architecture.md §4–§6, и с ними C становится полным.

Шкала: Б — блокер, решить до принятия ADR-013; Р — риск, решить в ADR или завести долговую задачу; З — замечание.

2. Находки

F1 (Б) Вложенный Navigator в нижней шторке занимает всю высоту

Суть. d7 и §4 черновика строят PluginsSheet на «вложенном Navigator: List, Detail, Auth». RenderTheater навигатора rtwk при ограниченных constraints берёт max_width × max_height (rtwk/src/navigation/navigator.rs:2650-2661). Шторка показывается через show_dialog с Alignment::BOTTOM_CENTER (src/sheets/mod.rs:19-27), и её constraints ограничены экраном. Значит, шторка с навигатором внутри становится высотой во весь экран. У оракула высота панели равна высоте её содержимого. Кроме того, PageRoute по умолчанию въезжает справа, а закрытые маршруты рисуются под новым, затемнёнными (navigator.rs:1688-1691). У оракула нет ни анимации, ни просвечивания. И по Esc на первой странице ключ уходит дальше навигатора (navigator.rs:1693-1699): это нужное поведение, но тогда Esc во время загрузки надо явно держать PopScope. Исправление. Страницы шторки — это декларативный локальный стек в её State: SheetStack<Page>, рисуется верхняя страница, контроллеры нижних страниц хранятся в записях стека. Это аналог Navigator 2.0 pages:; в rtwk есть только императивный Navigator. Возврат по Esc к родителю с курсором на исходной строке (kept) получается сам: ListController нижней страницы цел. Страница, которую требует домен (F2), — простое присваивание. Тесты засевают стек через аргумент initial. Navigator остаётся только для страниц (PageRoute) и корневых диалогов. Если человек хочет именно Navigator, нужен прототип и gap в rtwk («навигатор по размеру верхнего маршрута»).

F2 (Б) Открытие поверхности по воле домена не покрыто

Суть. Черновик: «открыта ли поверхность» — это State виджета, «core не знает ни страниц». Но оракул открывает поверхности из обработчиков ответов. После успешного install с приложениями, которым нужна авторизация, оракул вызывает open_plugin_install_auth_popup (chatwidget/plugins.rs:483-486). Тот сначала пробует replace_selection_view_if_active, а если вид не активен, делает show_selection_view (:840-851): шторка открывается, даже если пользователь её закрыл. Ошибка install, наоборот, заменяет вид только если он активен (:491-499). В порте это сейчас поле Plugins.shown («The setup of apps wants to be shown whether or not a menu is», core/src/screens/select/plugins.rs:224-225), и оно попадает под «открыта ли поверхность». Тот же род: запросы сервера (approvals, elicitation; уже есть presenter src/sheets/presenter.rs), стартовые промпты (onboarding::Model.prompts, core/src/screens/onboarding.rs:83), шаги onboarding. Исправление. Пятый род в IO-тесте: «желание показать» — доменный факт, у которого есть потребитель-поверхность. Core держит очередь SurfaceWish { seq, scope, kind } (как RequestQueue). Один UI-SurfacePresenter — обобщение существующего presenter запросов, ADR-002 «BlocListener» — открывает поверхность, если она закрыта, или просит открытую перейти на страницу. Каждое желание показывается один раз: presenter помнит последний показанный seq. Ошибка, которая «заменяет вид, только если он открыт», в желания не попадает: открытая шторка выводит страницу из Op::Failed сама (F3).

F3 (Б) Корреляция «жест → ответ»: тикета UI не знает

Суть. Черновик: «шаг после ответа ключуется тикетом операции», d6: «страница = f от Detail и ops id». Но тикет чеканится внутри apply (TicketMint в CodexApp, core/src/app.rs:550). Шторка отправляет глагол через ingress (cx.emit(&hs.screen, …), src/sheets/select/dialog.rs:113-139) и тикета не получает. В том же flush проекция ещё старая (G14; ADR-002 условие 4, architecture.md:253-257). Значит, если шторка решит по select сразу после emit, она один кадр увидит «нет операции». Двойное нажатие Enter на Install даст два глагола, и черновик не говорит, кто их схлопывает. Исправление. (а) Операции фичи ключуются доменным ключом цели: ops: Map<OpKey, Op>, где OpKey::Install(PluginId), и у Op есть gen. Core игнорирует повторный глагол, пока операция с тем же ключом в полёте (идемпотентность). Двойное нажатие безвредно. (б) Шторка держит локальное awaiting: Option<(OpKey, gen_before)> с момента emit. Пока домен не покажет gen > gen_before, она рисует «загрузку» из своего awaiting, а не из проекции. Так нет ни мерцания, ни решения по той же проекции в том же flush. (в) Тикет остаётся внутренним делом core (R1) и в UI не выходит.

F4 (Б) «Интерес» поверхности: кто шлёт Close

Суть. Черновик противоречит сам себе: в тексте ADR «открыта ли поверхность» отдана UI, в §3 «query/range живут в CodexApp с явными Open/Close». Домену знание об открытости действительно нужно, чтобы:

  • загрузить при открытии (/plugins → plugin/list);
  • остановить опрос, когда поверхность закрыта (agents center);
  • запросить заново при переподключении то, что открыто;
  • отбросить ответ, который уже никому не нужен.

Если Close шлёт обработчик Esc, то закрытие другими путями даст «вечно открыто». Другие пути: снятие маршрута при смене потока, перемонтирование по GlobalKey, выход через debug-меню, pop_until. Исправление. Один виджет Interest { key, child }. Он берёт Hs в did_change_dependencies и шлёт Intent::Interest(key, Open) в init_state, а Close — в dispose_with. rtwk разрешает в dispose_with вызывать emit в обработчик другого элемента, но предков там уже не прочитать, поэтому обработчик надо взять раньше (rtwk-framework/src/widget.rs:596-613). Core считает ссылки на каждый ключ. При attach он заново спрашивает ключи с ненулевым счётчиком. Правило: Intent::Interest создаётся только в widgets/interest.rs.

F5 (Р) Смена потока и шторки

Суть. Шторки — маршруты корневого навигатора (src/sheets/mod.rs:19-27; select::open — ближайшего, src/sheets/select/mod.rs:458-468). Смену потока они переживают. Оракул при смене потока заменяет ChatWidget целиком (app/session_lifecycle.rs:547), и его стек видов нижней панели теряется. Если в C шторка действует «на активный поток», пик после смены попадёт не в тот поток. Отдельно: страница сессии не ключуется ThreadId. Её корень ключуется (read_only, provider) (src/pages/session/session_page.rs:1143-1144), а помощника thread_scope, которого требует R2 (architecture.md:532), в коде нет (grep пуст). В C в State уйдёт больше состояния, и всё, что под страницей сессии, будет протекать между потоками. Исправление. (а) Аргументы шторки, привязанной к потоку, несут ThreadId (R14). Предикат жизни scope == session.active; при false шторка закрывается сама (§6.4 архитектуры) — паритет с оракулом. (б) thread_scope(id, child) ключует поддерево потока по ThreadId; что должно пережить переключение, лежит в ThreadUi. Правило r2_thread_subtree_is_keyed (единственное место ключа — thread_scope).

F6 (Р) Переподключение оставляет операции в полёте

Суть. attach_backend чистит только запросы сервера (drop_requests_of, core/src/app.rs:887-933). outgoing (наши RPC) не трогает. Ответы старой эпохи ingest отбрасывает (:940). Значит, ответ на plugin/install, отправленный до разрыва, не придёт никогда, и Op::Installing повиснет навсегда. Со стороны домена это будет вечный спиннер. Проверено чтением; тест-воспроизведение не запускал. Исправление. На attach разрешать все outgoing этого backend синтетическим Err(RpcError::Disconnected) через pending.resolve, чтобы Remote/Op перешли в Failed. Затем перезапросить открытые интересы (F4). Тест в core/tests/adr003.rs: «install → reconnect → op Failed, plugin/list спрошен заново».

F7 (Р) Директивы «домен → контроллер»

Суть. Домен пишет в контроллеры UI четырьмя самодельными слушателями в State страницы сессии: last_submit, restore, replayed_submissions, backtrack.restore (src/pages/session/session_page.rs:340-420, поля :74-82). Источник — seq в ThreadModel (give_back, core/src/threads.rs:2994-3005). «Виденный seq» хранится в одном State вместе с ThreadId. Если seq потока A вырос, пока показан B, то при возврате на A условие *thread == restore.0 ложно, и восстановление пропускается. Сообщения, отданные потоком A в фоне (например, отказ steer), в композер A не попадут. Это вывод из кода, тестом не проверено. Черновик этот род не упоминает. Исправление. Тип Directive<T> { seq, value } в core, по одному на род. «Виденный seq» лежит в ThreadUi своего потока (ThreadUi.seen: DirectiveSeen), а не в State страницы. Слушатель один на род (widgets/directives.rs). Правило: Directive читается только там.

F8 (Р) Правило 1 бьёт по kit и остаётся текстовым

Суть. adr013_core_states_hold_no_draw_state проверяет все поля структур в screens/features по списку имён. Законные типы kit держат состояние отрисовки, потому что ими владеет UI:

  • History.history_cursor (core/src/screens/composer/history.rs:266-280), владелец — ComposerDraft в ThreadUi;
  • машина Backtrack (src/widgets/thread_ui.rs:36-49);
  • CommandPopup.state: ScrollState (core/src/commands.rs:858-866), считается на каждый вызов из src/pages/session/popup.rs:46.

Правило либо даст ложные срабатывания, либо получит список исключений, который снова протечёт. Исправление. Сначала перенести kit в core::kit (только путь модуля, логика не меняется). Правило 1 смотрит типы, достижимые из корней домена: CodexApp, ThreadModel, FeatureStates, ScreenStates. Правило 5 в обратную сторону: тип из core::kit не бывает полем типа домена. Ratchet — на число нарушений, не на имена.

F9 (Р) Фикстуры и debug-входы

Суть. Шаги screen засевают формы UI, которые разбирает core: SeedEv::List(list) → Menu::List (core/src/screens/select.rs:1650-1680), List выводит serde::Deserialize (core/src/screens/select/list.rs:10). Когда list.rs уедет в widgets/picker, core не сможет разобрать шаг. EntryOpen — fn(&Seeded) -> AnyWidget без данных (src/app/debug/mod.rs:33-42), так что «шаг → DebugEntry.open» не механический перенос. Ещё: seeded-scope даёт свою модель только своему маршруту, поэтому шторки там открываются на ближайшем навигаторе (use_root_navigator: false, src/sheets/select/mod.rs:458-468). Это условие должно стать правилом, иначе в debug-входе шторка прочтёт живую модель. Исправление. Новый род шага ui ({"step":"ui","open":"select.list","props":{…}}). Core отдаёт его тестеру и входу как есть, так же как уже отдаёт key и resize (core/src/fixtures/script.rs:25-26). Вход UI разбирает props в аргументы поверхности (initial стек шторки, List для picker). Имена входов (dir, entry) сохраняются, поэтому 2 622 теста kit не меняются, меняются только фикстуры. Правило: шторка открывается только через sheets::open(cx, …), а он выбирает навигатор.

F10 (Р) Производительность и уведомления

Суть.

  • ScreenStates — один Rc на 19 моделей (core/src/app.rs:546). Каждое изменение делает Rc::make_mut, и, пока провайдер держит второй Rc, клонируется всё, кроме Shared (комментарий core/src/screens/popovers.rs:44-46).
  • Сейчас по этому пути идёт каждое движение курсора в меню (Intent::Choose/Cursor).
  • 27 мест делают watch::<ScreenStates> целиком (grep). Каждое изменение любого экрана перестраивает их все.
  • MenuDialog смотрит целиком сознательно: rtwk не сообщает зависимому, который уже грязный, об изменении, если тот только select-ит (src/sheets/select/dialog.rs:88-94).
  • В C одна FeatureStates на все фичи повторит ту же картину.

Исправление. (а) C убирает курсор и страницы с горячего пути: это локальный setState и перестройка одного поддерева. (б) Срезы Rc по экрану и по фиче (ScreenStates → поля Rc<…>, провайдер на срез) и select по срезу. (в) Особенность select записать в rtwk-gaps как gap (ведёт человек). До исправления закрытие по воле домена смотрит маленький срез через watch. (г) Правило: watch::<ScreenStates> и watch::<FeatureStates> запрещены, ratchet от 27.

F11 (Р) Шторка-оверлей или докнутая панель

Суть. У оракула виды нижней панели стоят на месте композера: высота панели растёт, а хвост транскрипта поднимается и остаётся виден. Шторки порта — диалоги-оверлеи у нижнего края (src/sheets/mod.rs:19-27). Если шторка выше композера, она закрывает нижние строки транскрипта. rtwk-gaps.md:101 (G28) прямо называет недостающее: «a docked bottom pane that replaces the composer». Во Flutter есть оба варианта: Scaffold.bottomSheet (докнутая, часть раскладки) и showModalBottomSheet (маршрут). У Scaffold в rtwk нижнего слота нет (rtwk/src/navigation/scaffold.rs:684-719), но слот собирается композицией. Исправление. Это открытое решение О2 в architecture.md. Рекомендация: SheetHost — слот в Column страницы сессии под транскриптом. Его содержимое — SheetStack (F1), он сам внутри thread_scope (F5), поэтому смена потока сбрасывает его, как у оракула. Через show_dialog идут только центрированные виды оракула и настоящие диалоги. Сначала сверить по снимку оракула: popup поверх длинного транскрипта.

F12 (Р) Клавиши и keymap

Суть. KeyCode:: встречается 280 раз в 31 файле pages/sheets/widgets, keymap(cx) читается в 22 местах. Страница сессии биндит keys::defaults(), то есть дефолты оракула, а не настроенный keymap (src/pages/session/session_page.rs:1136-1138; модуль src/pages/session/keys.rs:1-7 сам говорит «will replace»). Когда шторки уйдут в UI, перепривязка tui.keymap.* до них не дойдёт. Исправление. Разбор и разрешение keymap — в core (core/src/keymap, это конфиг). Каждая поверхность объявляет свои Intent rtwk и строит Shortcuts из Keymap контекста. Actions — в State поверхности. Правило ratchet: KeyCode:: только в src/keymap/ и примитивах widgets/.

F13 (З) Критерий (3) IO-теста размыт

«Его читает другой экран, поток или шаг жизненного цикла». Под это подпадает почти всё: футер читает выбранную модель, но это домен из конфига, а не курсор пикера. Нужна формулировка по владельцу записи плюс таблица трудных случаев (§3 ниже). Вписано в architecture.md §1.3.

F14 (З) Поправка 2026-11-18 уже наполовину отменена

В коде слот под транскриптом заменён на show_dialog у нижнего края (src/sheets/mod.rs, по поправке 2026-11-19b). От поправки 2026-11-18 осталось «core view stack» (select.stack). ADR-013 должен снять её целиком и сказать, где теперь живёт стек (F1, F11).

F15 (З) Двойной владелец на время переезда

Пока семейство меню переезжает, select.stack и новый SheetStack могут держать одну шторку. Правило: семейство (Menu::X) переезжает целиком за один коммит. hub_budget.txt уменьшается в том же коммите, а смешанное семейство (вариант Menu::X и SheetStack для X одновременно) ловит проверка в hub_enums_only_shrink (по списку переехавших).

stateful eq для экранов и шторок есть в тексте (architecture.md:246-247), а правило есть только для ключа навигатора (adr002_the_navigator_is_keyed, tests/rules/rules.rs:132). В C шторок со State станет больше. Нужно adr002_screen_and_sheet_widgets_are_eq.
