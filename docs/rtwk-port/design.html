Codex CLI on rtwk — target architecture (design to review)

What the finished phase-1 app looks like, drawn to be looked at, weighed and changed before the migration starts. Text decisions: architecture.md. Rendered: design.html. App state follows ADR-003, accepted by the person 2026-11-17: plain model, thread-scoped apply -> Effects, intents on shared state as values, rules R1–R14 (§6b). Corrected after the independent review reviews/arch-review.md: navigation and dialogs as in twk — Navigator + PageRoute, show_dialog, live data through rtwk::provider projections of the model (§2, §3, §7, §8), ThreadUi for per-thread widget state, held in the UI model, not the core one (§6), the shell spawns through rtwk-tokio (§4, §5), split pending maps (§6), counts in §6b.

3. Crate and module layout

Two crates in one workspace and the arrows that are allowed (§3b says which rule holds each one): the core has no rtwk and no direct runtime or IO dependency (the protocol crate pulls tokio in transitively); the UI crate holds the views, the shell and the composition root; the host is the binary's backend.

4. Runtime: an event from the backend reaches the screen

sequenceDiagram
  participant AS as app-server
  participant T as shell subscription (tokio, rtwk-tokio)
  participant IN as ingress router (UI thread)
  participant TM as ThreadModel of thread X
  participant V as view(&state)
  participant R as rtwk
  AS->>T: notification (thread X, turn, item, delta)
  T->>IN: ThreadEv for X, stamped with the epoch captured when this subscription was created
  Note over IN: R1 drops events of an older epoch. User intents enter the same stream (R10)
  IN->>TM: apply(ThreadModel X, ThreadEv, ThreadFx X)
  Note over TM: R3 it can touch only thread X. R4 transcript upsert by (TurnId, ItemId), so a repeat updates and never duplicates. A resume snapshot replaces its turns wholesale
  TM->>TM: Versioned slices it touched bump their rev (memo deps carry rev plus Rc data)
  IN->>V: one view run for everything applied this flush
  V->>V: derived values computed (R7), memo subtrees with unchanged revisions reused
  V->>R: widget tree
  R->>R: rebuild changed elements, layout, paint, diff
  Note over R: the terminal shows the frame

5. Runtime: a user action and a late reply

sequenceDiagram
  participant U as user
  participant R as rtwk (Focus, Shortcuts)
  participant H as handler cx.on
  participant IN as ingress stream
  participant M as model apply
  participant SH as shell (the only place that spawns, rtwk-tokio)
  participant AS as app-server
  U->>R: Enter in the composer of thread X
  R->>H: action
  H->>IN: Intent Submit for thread X, text from the composer controller of ThreadUi (R10)
  IN->>M: in arrival order, after events already received
  M->>M: TurnState Idle to Running (R5), outgoing ticket 7 for (X, Ticket) (R3, R13)
  M-->>SH: Effects: Rpc start turn, ticket 7
  SH->>AS: request
  U->>R: switches to thread Y
  AS-->>SH: reply for ticket 7
  SH->>IN: Reply of T for ticket 7
  IN->>M: Reply of T for ticket 7
  M->>M: pending.resolve(reply) checks the ticket (R1): still current, so applied to X only
  Note over M: had the turn been interrupted, the ticket would be gone and the reply dropped by construction

6. App state shape

classDiagram
  class CodexApp {
    session: Session
    threads: ThreadId to ThreadModel map
    active: ThreadId
    settings: Settings
    account: Account
    agents: AgentsState
  }
  class ThreadModel {
    queue: submitted messages (R2)
    transcript: ordered map by TurnId and ItemId, upsert; snapshot replaces (R4)
    turn: TurnState (R5)
    outgoing: ThreadId and Ticket to Ctx (R1, R3)
    server_requests: ConnEpoch, ThreadId, ServerRequestId to Approval (R3, R13)
    tokens: Versioned Usage
  }
  class UiApp {
    core: CodexApp
    ui: UiState
    link: shell Link
  }
  class UiState {
    nav_key: GlobalKey
    thread_ui: ThreadUiMap
    lang: Lang
    debug: bool
  }
  class ThreadUi {
    in UiState, written by R14-allowlisted UI modules, never in the core model, not seen by apply
    composer: TextEditingController
    scroll, selection controllers
  }
  class TurnState {
    Idle
    Running(RunningTurn: streams, hooks, prompts, reviews)
  }
  class Remote {
    Loading
    Loaded(value, fetched_at, generation)
    Failed
  }
  class Approval {
    id: ServerRequestId scoped by ConnEpoch (R13)
    kind: Exec, Patch, Permissions, Mcp, UserInput
  }
  class Session {
    state: Starting, Ready, Failed
    backend
    conn_epoch: ConnEpoch, changes arrive as events
    rate_limits: Remote (R6)
    attach_epoch per thread (R1)
  }
  CodexApp --> ThreadModel
  ThreadModel --> TurnState
  ThreadModel --> Approval
  UiApp --> CodexApp : core
  UiApp --> UiState : ui
  UiApp ..> Link : link, the app's end of the shell
  UiState --> ThreadUi : keyed by ThreadId
  CodexApp --> Session
  Session --> Remote

Derived (functions of the model, never stored, R7): per-thread unread and running, total tokens, sidebar filter results, agents-center counts, footer hints, what the status line shows, can_submit and other predicates (R8). Not allowed: app data in rtwk widget-local state (Obs, use_state, hand-written State, controllers) outside UI-only modules — R14; IO in apply or views — R12; the clock read in views — R11. ThreadUi, kept in the UI model (UiApp.ui) and never in CodexApp, holds per-thread controllers (composer text, scroll, selection) so A→B→A keeps them; the model never mirrors the draft — the text enters apply as an intent on submit. App-scoped events (account, rate limits, app-level MCP startup) go through apply_app(&mut CodexApp, AppEv, &mut AppFx).

Checked on codex-tui's real history (research/state-bug-classes.md; the report for openai/codex developers: reports/tui-bug-classes.html). Mandatory tests the rules imply: switch round-trip (A→B→A), end-path matrix (complete / interrupt / fail × feature), event-permutation property tests, lifecycle × intent table, Model::assert_consistent() after every event. Lints (own clippy.toml; crate-wide deny, #[allow] only on allowlisted modules, a CI grep rejects other allows): every spawn path outside the shell (AppCx::spawn, Cx::spawn, rtwk-tokio spawn/subscribe/follow, std::thread::spawn, tokio::spawn, AppCx::channel), Obs/use_state/ hand-written State/controllers outside UI-only modules, Instant::now/SystemTime::now in views, blocking IO in apply/views. Plus the resume/reconnect-mid-turn test (transcript equals the snapshot).

7. Navigation map (screens of architecture.md §1)

As in twk: the root is a Navigator (home: chat) under a MultiProvider of model projections. Screens (solid arrows) are PageRoutes pushed by the widget that opens them and read live data with select / watch. Dialogs (dotted) open with show_dialog from the asking widget. Backend requests (approvals, elicitations, user input, startup prompts) open through the request presenter and close themselves when the model drops the request. Routes and dialogs get ids; results return to the model as ticketed events.
