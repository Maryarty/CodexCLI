## 0. Вердикт

**Направление C верное. Принимать ADR-013 в черновой редакции нельзя: в нём четыре блокера.** Диагноз отчёта подтверждается кодом: «модель экрана» в core, двери на каждую форму UI, дырявое правило. IO-тест разделяет состояние правильно. Но черновик держит только путь «жест → глагол → домен → проекция». Четыре других пути, которые оракул использует постоянно, в нём не описаны:

1. домен сам открывает поверхность (оракул открывает шторку авторизации после ответа install, даже если пользователь её закрыл);
2. домен пишет в контроллер UI (вернуть сообщения в композер, префилл после backtrack, запись истории);
3. поверхность заявляет интерес к данным (открыта или закрыта), и домен должен знать это при переподключении;
4. UI сопоставляет ответ со своим жестом, хотя тикет чеканит core.

Сверх того, предложенный механизм (вложенный `Navigator` в нижней шторке) в rtwk занимает всю высоту экрана. Всё это решается небольшими общими механизмами. Они описаны в architecture.md §4–§6, и с ними C становится полным.

Шкала: **Б** — блокер, решить до принятия ADR-013; **Р** — риск, решить в ADR или завести долговую задачу; **З** — замечание.

## 2. Находки

### F1 (Б) Вложенный `Navigator` в нижней шторке занимает всю высоту
**Суть.** d7 и §4 черновика строят `PluginsSheet` на «вложенном Navigator: List, Detail, Auth». `RenderTheater` навигатора rtwk при ограниченных constraints берёт `max_width × max_height` (rtwk/src/navigation/navigator.rs:2650-2661). Шторка показывается через `show_dialog` с `Alignment::BOTTOM_CENTER` (src/sheets/mod.rs:19-27), и её constraints ограничены экраном. Значит, шторка с навигатором внутри становится высотой во весь экран. У оракула высота панели равна высоте её содержимого. Кроме того, `PageRoute` по умолчанию въезжает справа, а закрытые маршруты рисуются под новым, затемнёнными (navigator.rs:1688-1691). У оракула нет ни анимации, ни просвечивания. И по Esc на первой странице ключ уходит дальше навигатора (navigator.rs:1693-1699): это нужное поведение, но тогда Esc во время загрузки надо явно держать `PopScope`.
**Исправление.** Страницы шторки — это декларативный локальный стек в её `State`: `SheetStack<Page>`, рисуется верхняя страница, контроллеры нижних страниц хранятся в записях стека. Это аналог Navigator 2.0 `pages:`; в rtwk есть только императивный Navigator. Возврат по Esc к родителю с курсором на исходной строке (`kept`) получается сам: `ListController` нижней страницы цел. Страница, которую требует домен (F2), — простое присваивание. Тесты засевают стек через аргумент `initial`. `Navigator` остаётся только для страниц (`PageRoute`) и корневых диалогов. Если человек хочет именно Navigator, нужен прототип и gap в rtwk («навигатор по размеру верхнего маршрута»).

### F2 (Б) Открытие поверхности по воле домена не покрыто
**Суть.** Черновик: «открыта ли поверхность» — это `State` виджета, «core не знает ни страниц». Но оракул открывает поверхности из обработчиков ответов. После успешного install с приложениями, которым нужна авторизация, оракул вызывает `open_plugin_install_auth_popup` (chatwidget/plugins.rs:483-486). Тот сначала пробует `replace_selection_view_if_active`, а если вид не активен, делает `show_selection_view` (:840-851): шторка открывается, даже если пользователь её закрыл. Ошибка install, наоборот, заменяет вид только если он активен (:491-499). В порте это сейчас поле `Plugins.shown` («The setup of apps wants to be shown whether or not a menu is», core/src/screens/select/plugins.rs:224-225), и оно попадает под «открыта ли поверхность». Тот же род: запросы сервера (approvals, elicitation; уже есть presenter src/sheets/presenter.rs), стартовые промпты (`onboarding::Model.prompts`, core/src/screens/onboarding.rs:83), шаги onboarding.
**Исправление.** Пятый род в IO-тесте: **«желание показать»** — доменный факт, у которого есть потребитель-поверхность. Core держит очередь `SurfaceWish { seq, scope, kind }` (как `RequestQueue`). Один UI-`SurfacePresenter` — обобщение существующего presenter запросов, ADR-002 «BlocListener» — открывает поверхность, если она закрыта, или просит открытую перейти на страницу. Каждое желание показывается один раз: presenter помнит последний показанный seq. Ошибка, которая «заменяет вид, только если он открыт», в желания не попадает: открытая шторка выводит страницу из `Op::Failed` сама (F3).

### F3 (Б) Корреляция «жест → ответ»: тикета UI не знает
**Суть.** Черновик: «шаг после ответа ключуется тикетом операции», d6: «страница = f от Detail и ops id». Но тикет чеканится внутри `apply` (`TicketMint` в `CodexApp`, core/src/app.rs:550). Шторка отправляет глагол через ingress (`cx.emit(&hs.screen, …)`, src/sheets/select/dialog.rs:113-139) и тикета не получает. В том же flush проекция ещё старая (G14; ADR-002 условие 4, architecture.md:253-257). Значит, если шторка решит по `select` сразу после emit, она один кадр увидит «нет операции». Двойное нажатие Enter на Install даст два глагола, и черновик не говорит, кто их схлопывает.
**Исправление.** (а) Операции фичи ключуются **доменным ключом** цели: `ops: Map<OpKey, Op>`, где `OpKey::Install(PluginId)`, и у `Op` есть `gen`. Core игнорирует повторный глагол, пока операция с тем же ключом в полёте (идемпотентность). Двойное нажатие безвредно. (б) Шторка держит локальное `awaiting: Option<(OpKey, gen_before)>` с момента emit. Пока домен не покажет `gen > gen_before`, она рисует «загрузку» из своего `awaiting`, а не из проекции. Так нет ни мерцания, ни решения по той же проекции в том же flush. (в) Тикет остаётся внутренним делом core (R1) и в UI не выходит.

### F4 (Б) «Интерес» поверхности: кто шлёт Close
**Суть.** Черновик противоречит сам себе: в тексте ADR «открыта ли поверхность» отдана UI, в §3 «query/range живут в CodexApp с явными Open/Close». Домену знание об открытости действительно нужно, чтобы:
- загрузить при открытии (`/plugins` → `plugin/list`);
- остановить опрос, когда поверхность закрыта (agents center);
- запросить заново при переподключении то, что открыто;
- отбросить ответ, который уже никому не нужен.

Если Close шлёт обработчик Esc, то закрытие другими путями даст «вечно открыто». Другие пути: снятие маршрута при смене потока, перемонтирование по `GlobalKey`, выход через debug-меню, `pop_until`.
**Исправление.** Один виджет `Interest { key, child }`. Он берёт `Hs` в `did_change_dependencies` и шлёт `Intent::Interest(key, Open)` в `init_state`, а `Close` — в `dispose_with`. rtwk разрешает в `dispose_with` вызывать `emit` в обработчик другого элемента, но предков там уже не прочитать, поэтому обработчик надо взять раньше (rtwk-framework/src/widget.rs:596-613). Core считает ссылки на каждый ключ. При `attach` он заново спрашивает ключи с ненулевым счётчиком. Правило: `Intent::Interest` создаётся только в `widgets/interest.rs`.

### F5 (Р) Смена потока и шторки
**Суть.** Шторки — маршруты корневого навигатора (src/sheets/mod.rs:19-27; `select::open` — ближайшего, src/sheets/select/mod.rs:458-468). Смену потока они переживают. Оракул при смене потока заменяет `ChatWidget` целиком (app/session_lifecycle.rs:547), и его стек видов нижней панели теряется. Если в C шторка действует «на активный поток», пик после смены попадёт не в тот поток. Отдельно: страница сессии не ключуется `ThreadId`. Её корень ключуется `(read_only, provider)` (src/pages/session/session_page.rs:1143-1144), а помощника `thread_scope`, которого требует R2 (architecture.md:532), в коде нет (grep пуст). В C в `State` уйдёт больше состояния, и всё, что под страницей сессии, будет протекать между потоками.
**Исправление.** (а) Аргументы шторки, привязанной к потоку, несут `ThreadId` (R14). Предикат жизни `scope == session.active`; при `false` шторка закрывается сама (§6.4 архитектуры) — паритет с оракулом. (б) `thread_scope(id, child)` ключует поддерево потока по `ThreadId`; что должно пережить переключение, лежит в `ThreadUi`. Правило `r2_thread_subtree_is_keyed` (единственное место ключа — `thread_scope`).

### F6 (Р) Переподключение оставляет операции в полёте
**Суть.** `attach_backend` чистит только запросы сервера (`drop_requests_of`, core/src/app.rs:887-933). `outgoing` (наши RPC) не трогает. Ответы старой эпохи `ingest` отбрасывает (:940). Значит, ответ на `plugin/install`, отправленный до разрыва, не придёт никогда, и `Op::Installing` повиснет навсегда. Со стороны домена это будет вечный спиннер. Проверено чтением; тест-воспроизведение не запускал.
**Исправление.** На `attach` разрешать все `outgoing` этого backend синтетическим `Err(RpcError::Disconnected)` через `pending.resolve`, чтобы `Remote`/`Op` перешли в `Failed`. Затем перезапросить открытые интересы (F4). Тест в core/tests/adr003.rs: «install → reconnect → op Failed, plugin/list спрошен заново».

### F7 (Р) Директивы «домен → контроллер»
**Суть.** Домен пишет в контроллеры UI четырьмя самодельными слушателями в `State` страницы сессии: `last_submit`, `restore`, `replayed_submissions`, `backtrack.restore` (src/pages/session/session_page.rs:340-420, поля :74-82). Источник — seq в `ThreadModel` (`give_back`, core/src/threads.rs:2994-3005). «Виденный seq» хранится в одном `State` вместе с `ThreadId`. Если seq потока A вырос, пока показан B, то при возврате на A условие `*thread == restore.0` ложно, и восстановление пропускается. Сообщения, отданные потоком A в фоне (например, отказ steer), в композер A не попадут. Это вывод из кода, тестом не проверено. Черновик этот род не упоминает.
**Исправление.** Тип `Directive<T> { seq, value }` в core, по одному на род. «Виденный seq» лежит в `ThreadUi` своего потока (`ThreadUi.seen: DirectiveSeen`), а не в `State` страницы. Слушатель один на род (`widgets/directives.rs`). Правило: `Directive` читается только там.

### F8 (Р) Правило 1 бьёт по kit и остаётся текстовым
**Суть.** `adr013_core_states_hold_no_draw_state` проверяет все поля структур в screens/features по списку имён. Законные типы kit держат состояние отрисовки, потому что ими владеет UI:
- `History.history_cursor` (core/src/screens/composer/history.rs:266-280), владелец — `ComposerDraft` в `ThreadUi`;
- машина `Backtrack` (src/widgets/thread_ui.rs:36-49);
- `CommandPopup.state: ScrollState` (core/src/commands.rs:858-866), считается на каждый вызов из src/pages/session/popup.rs:46.

Правило либо даст ложные срабатывания, либо получит список исключений, который снова протечёт.
**Исправление.** Сначала перенести kit в `core::kit` (только путь модуля, логика не меняется). Правило 1 смотрит типы, **достижимые из корней домена**: `CodexApp`, `ThreadModel`, `FeatureStates`, `ScreenStates`. Правило 5 в обратную сторону: тип из `core::kit` не бывает полем типа домена. Ratchet — на число нарушений, не на имена.

### F9 (Р) Фикстуры и debug-входы
**Суть.** Шаги `screen` засевают формы UI, которые разбирает core: `SeedEv::List(list)` → `Menu::List` (core/src/screens/select.rs:1650-1680), `List` выводит `serde::Deserialize` (core/src/screens/select/list.rs:10). Когда `list.rs` уедет в `widgets/picker`, core не сможет разобрать шаг. `EntryOpen` — `fn(&Seeded) -> AnyWidget` без данных (src/app/debug/mod.rs:33-42), так что «шаг → `DebugEntry.open`» не механический перенос. Ещё: seeded-scope даёт свою модель только своему маршруту, поэтому шторки там открываются на ближайшем навигаторе (`use_root_navigator: false`, src/sheets/select/mod.rs:458-468). Это условие должно стать правилом, иначе в debug-входе шторка прочтёт живую модель.
**Исправление.** Новый род шага `ui` (`{"step":"ui","open":"select.list","props":{…}}`). Core отдаёт его тестеру и входу как есть, так же как уже отдаёт `key` и `resize` (core/src/fixtures/script.rs:25-26). Вход UI разбирает `props` в аргументы поверхности (`initial` стек шторки, `List` для picker). Имена входов (`dir`, `entry`) сохраняются, поэтому 2 622 теста kit не меняются, меняются только фикстуры. Правило: шторка открывается только через `sheets::open(cx, …)`, а он выбирает навигатор.

### F10 (Р) Производительность и уведомления
**Суть.**
- `ScreenStates` — один `Rc` на 19 моделей (core/src/app.rs:546). Каждое изменение делает `Rc::make_mut`, и, пока провайдер держит второй `Rc`, клонируется всё, кроме `Shared` (комментарий core/src/screens/popovers.rs:44-46).
- Сейчас по этому пути идёт каждое движение курсора в меню (`Intent::Choose/Cursor`).
- 27 мест делают `watch::<ScreenStates>` целиком (grep). Каждое изменение любого экрана перестраивает их все.
- `MenuDialog` смотрит целиком сознательно: rtwk не сообщает зависимому, который уже грязный, об изменении, если тот только `select`-ит (src/sheets/select/dialog.rs:88-94).
- В C одна `FeatureStates` на все фичи повторит ту же картину.

**Исправление.** (а) C убирает курсор и страницы с горячего пути: это локальный `setState` и перестройка одного поддерева. (б) Срезы `Rc` по экрану и по фиче (`ScreenStates` → поля `Rc<…>`, провайдер на срез) и `select` по срезу. (в) Особенность `select` записать в rtwk-gaps как gap (ведёт человек). До исправления закрытие по воле домена смотрит маленький срез через `watch`. (г) Правило: `watch::<ScreenStates>` и `watch::<FeatureStates>` запрещены, ratchet от 27.

### F11 (Р) Шторка-оверлей или докнутая панель
**Суть.** У оракула виды нижней панели стоят на месте композера: высота панели растёт, а хвост транскрипта поднимается и остаётся виден. Шторки порта — диалоги-оверлеи у нижнего края (src/sheets/mod.rs:19-27). Если шторка выше композера, она закрывает нижние строки транскрипта. rtwk-gaps.md:101 (G28) прямо называет недостающее: «a docked bottom pane that replaces the composer». Во Flutter есть оба варианта: `Scaffold.bottomSheet` (докнутая, часть раскладки) и `showModalBottomSheet` (маршрут). У `Scaffold` в rtwk нижнего слота нет (rtwk/src/navigation/scaffold.rs:684-719), но слот собирается композицией.
**Исправление.** Это открытое решение О2 в architecture.md. Рекомендация: `SheetHost` — слот в `Column` страницы сессии под транскриптом. Его содержимое — `SheetStack` (F1), он сам внутри `thread_scope` (F5), поэтому смена потока сбрасывает его, как у оракула. Через `show_dialog` идут только центрированные виды оракула и настоящие диалоги. Сначала сверить по снимку оракула: popup поверх длинного транскрипта.

### F12 (Р) Клавиши и keymap
**Суть.** `KeyCode::` встречается 280 раз в 31 файле pages/sheets/widgets, `keymap(cx)` читается в 22 местах. Страница сессии биндит `keys::defaults()`, то есть дефолты оракула, а не настроенный keymap (src/pages/session/session_page.rs:1136-1138; модуль src/pages/session/keys.rs:1-7 сам говорит «will replace»). Когда шторки уйдут в UI, перепривязка `tui.keymap.*` до них не дойдёт.
**Исправление.** Разбор и разрешение keymap — в core (`core/src/keymap`, это конфиг). Каждая поверхность объявляет свои `Intent` rtwk и строит `Shortcuts` из `Keymap` контекста. `Actions` — в `State` поверхности. Правило ratchet: `KeyCode::` только в `src/keymap/` и примитивах `widgets/`.

### F13 (З) Критерий (3) IO-теста размыт
«Его читает другой экран, поток или шаг жизненного цикла». Под это подпадает почти всё: футер читает выбранную модель, но это домен из конфига, а не курсор пикера. Нужна формулировка по владельцу записи плюс таблица трудных случаев (§3 ниже). Вписано в architecture.md §1.3.

### F14 (З) Поправка 2026-11-18 уже наполовину отменена
В коде слот под транскриптом заменён на `show_dialog` у нижнего края (src/sheets/mod.rs, по поправке 2026-11-19b). От поправки 2026-11-18 осталось «core view stack» (`select.stack`). ADR-013 должен снять её целиком и сказать, где теперь живёт стек (F1, F11).

### F15 (З) Двойной владелец на время переезда
Пока семейство меню переезжает, `select.stack` и новый `SheetStack` могут держать одну шторку. Правило: семейство (`Menu::X`) переезжает целиком за один коммит. `hub_budget.txt` уменьшается в том же коммите, а смешанное семейство (вариант `Menu::X` и `SheetStack` для X одновременно) ловит проверка в `hub_enums_only_shrink` (по списку переехавших).

### F16 (З) Условие 1 ADR-002 не проверяется
`stateful eq` для экранов и шторок есть в тексте (architecture.md:246-247), а правило есть только для ключа навигатора (`adr002_the_navigator_is_keyed`, tests/rules/rules.rs:132). В C шторок со `State` станет больше. Нужно `adr002_screen_and_sheet_widgets_are_eq`.

### F17 (З) Формулировки отчёта
- d5 «доменные части chat и status в ThreadModel, без slots экранов»: в C `ThreadSlots` остаются (доменная часть экранов на поток), уходят только поля отрисовки.
- «composer → core::kit, 0 строк в UI»: верно по путям, но `Store` истории — домен (`popovers::Model.history`, core/src/screens/popovers.rs:44-47), а навигация по истории — kit в `ThreadUi` (src/widgets/composer_draft.rs:26, :78).
- «2 622 oracle-теста без изменений» верно, только если имена входов сохраняются (F9).

## 3. Трудные случаи IO-теста: решения

| случай | что в core (домен) | что в UI | механизм |
|---|---|---|---|
| деталь плагина (`plugin/read`) | `details: Map<PluginKey, Remote<Detail>>` — кэш по параметру, без указателя «текущая» | страница `Detail(PluginKey)` в `SheetStack` | глагол `Read{key}` при показе страницы; поздний ответ ложится в кэш; страница = f(свой ключ, кэш) |
| install → auth | `ops[Install(key)]`, после ответа `SurfaceWish::PluginAuth{plugin}` | страница `Auth` | F2 + F3 |
| смена cwd во время открытой шторки | `scope` (cwd), `forget` при смене (plugins.rs:369-380); ответы другого cwd отбрасываются, как у оракула (chatwidget/plugins.rs:454-456) | шторка держит `scope` в аргументах, предикат жизни | закрытие по воле домена (§6.4) |
| approvals | `RequestQueue` (ключ эпоха+поток+id) | выделенная опция, черновик отказа с отзывом | presenter; шторка закрывается, когда запроса нет; при смене потока по предикату |
| `@` файлы | `FileMatches{query, matches}` (popovers.rs:39-40), запрос через host | открыт ли popup, выделение — `Autocomplete` | глагол `FileSearch{query}` при изменении текста; показ, только если `matches.query == текущий префикс` |
| `$` и `/` | каталог упоминаний — домен; фильтр `/` — kit (`CommandPopup`) | выделение | чистая функция над доменом |
| поиск resume | `Listing` по `query` + курсорам страниц, `previews` по ключу, `Remote<Transcript>` | текст поля — `TextEditingController`; плотность, развёрнутая строка, фокус тулбара | `Search{query}` (core не пишет текст обратно); `Cursor/Room/End` → `NeedMore`; `inline_error` с seq, UI помнит «погашенный» seq |
| Ctrl+T в resume | `Remote<Transcript>` по `ThreadId` | `awaiting: Option<ThreadId>`, маршрут пейджера | слушатель: пришёл и всё ещё ждём → push |
| onboarding | шаги — жизненный цикл (держат старт первого потока, `start_held`) | выделение опции, поле API-ключа | шаг = f(домен) |
| выделение и поиск транскрипта | — (данные в `ThreadModel`) | `SelectionArea`, запрос поиска, позиция | чистая функция поиска (kit) по `ThreadModel`, memo |
| backtrack | `Rollback{thread, n}` → `ThreadAsk`; снимок заменяет ходы; `Directive` префилла | машина `Backtrack` в `ThreadUi.modes` (как сейчас) | F7 |
| Ctrl+T пейджер | — | режим страницы сессии (`ThreadUi.modes`) | контроллер |
| смена потока | `session.active` (только `apply_app`) | `ThreadUi` по `ThreadId`; поддерево по ключу | `thread_scope`, предикаты жизни шторок (F5) |
| переподключение | эпоха; `outgoing` → `Failed`; перезапрос интересов | шторки остаются, видят `Remote::Loading` | F4, F6 |

## 4. Что C оставляет без ответа (в architecture.md как открытые решения)

О1 стек страниц шторки: `SheetStack` в `State` или вложенный `Navigator` (рекомендация — `SheetStack`, F1). О2 шторка докнутая или оверлей (рекомендация — докнутая для видов нижней панели оракула, F11). О3 где kit: `core::kit` или отдельный крейт (рекомендация — `core::kit`, проще для upstream). О4 ключ операций: доменный ключ или UI-корреляция (рекомендация — доменный ключ + `gen`). О5 кто пишет правила шага 0 и долговую задачу семантики IO-теста. О6 судьба WIP `6cafa8de1` (рекомендация отчёта — не сливать, пилот с нуля по C) и `95826e191` (сливать как есть). О7 `Rc` против `Arc` для upstream-core (уже открыт в architecture.md:1080-1084, ADR-013 его не меняет).
